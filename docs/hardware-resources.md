## 整机源码内存预算（2026-11-11）

结论：当前布局不能直接叠加全部模块。保留现有业务和升级入口后，若采用M2报告的RX池16块、PBUF池12块，普通SRAM静态分配已超出1248 B，尚未包含运行期C堆分配、完整配置和HTTPS。以下为源码及编译链接预算，不是运行峰值或整机验收。

### 统计范围与方法

- 基线为本地`main`、HEAD `826ac35`及当前未提交改动；没有fetch、合并或采用队友未合入的源码。M2扩池作为单独压力场景，不冒充其最新固件的map。
- AppDebug与Release常规构建检查通过。本轮临时链接以`--undefined`保留现有MQTT、Telemetry、网络/TF升级、维护帧、配置存储及校时等入口，避免未绑定入口被回收后低估资源；未修改正式任务绑定。
- 使用ARM GCC 14.3.1工具链的目标文件符号及ELF调试信息核对结构体大小，不执行主机C模型或固件。临时探针、ELF和map已清理，仅保留本地计算证据。
- 完整配置解析器、ControlValidate最终运行策略、HTTPS客户端及其线程尚未实现；相关内存不能记为0 B或写成已满足。临时保留现有入口也不等于最终功能已接通。
- 普通App预算容量为131008 B，首64 B邮箱另留；CCM为65536 B。Boot与App分时运行，RAM取各自峰值，不相加；两者主Flash分区仍分别为64 KiB和448 KiB。

已有`.su`中Storage读取路径单函数帧最高1560 B、Telemetry回调640 B、MQTT CONNECT组包560 B。它们不是完整调用链栈峰值；printf、密码库、回调与抢占上下文仍须合算。不能根据这些单帧数字缩栈，512 B Config栈也没有完整功能可供证明。

### 网络扩池与可回收空间

当前map对应RX每块1568 B、PBUF每块1532 B。将RX从6扩到16、PBUF从8扩到12，新增`10×1568 + 4×1532 = 21808 B`普通SRAM。以M2报告的修复作为压力条件，不通过缩回接收池掩盖DMA池耗尽问题。

| 场景 | 普通SRAM链接占用 | 普通SRAM链接余量 | CCM占用 / 余量 |
| --- | ---: | ---: | ---: |
| 保留现有入口，RX6/PBUF8 | 110448 B | 20560 B | 50264 B / 15272 B |
| 仅叠加RX16/PBUF12 | 132256 B | **超出1248 B** | 50264 B / 15272 B |
| 扩池 + 应用AES ROM查表候选 | 123512 B | 7496 B | 50264 B / 15272 B |
| 上述候选 + 补传批量10降4的算术预算 | 123512 B | 7496 B | 40472 B / 25064 B |

ROM查表已做临时编译链接对照，未更改正式配置：应用普通SRAM从110448 B降至101704 B，释放8744 B，Flash从372592 B增至380184 B。若同时对Boot启用，Boot Flash将增至63452 B、仅余2084 B；不应未经整体评估把此选项放入共用配置。对照只证明链接收益，不代表密码用例或运行验证通过。

补传批量候选仅计算既有三处`storage_fetch_resp_t`：M3组装区、值传递队列和M2接收区。每份从5448 B降至2184 B，可共减9792 B CCM；保持完整记录而分更多批发送。它尚未实现，需要M2/M3同时调整并验证补传吞吐与队列行为。

即使采用应用ROM查表并扩池，C堆理论跨度也只剩8008 B，放不下调整前16站9904 B的净表；当前4站净表为2512 B，扣除后理论仅余5496 B，尚未扣分配器开销、密码运算及完整配置的并发需求。能否容纳这些分配仍待核算，不能把上表7496 B链接余量视作最终功能可用预算。

### 未实现功能的资源边界

- **Modbus容量**：已按用户确认改为4站×16点，复用现有结构，不新增共享点池。每点32 B、每站616 B，含句柄共2512 B。先前32站/256总点及共享点池属于调整前方案，不再作为当前目标；完整配置的标识、周期等字段若增加，仍需计入后续预算。
- **配置**：64 KiB是外部Flash文件上限，三槽不占三份RAM。运行配置应只留一份必要索引和运行表，候选分块验证，保存重启生效；不得另建64 KiB输入缓冲或完整DOM。串口收发、解析状态、去重/引用索引、字符串工作区、存储代理消息及Config实际栈仍须逐项分配。写白名单和未启用模板条目尚无独立数量上限，仅有64 KiB文件限制，不能擅自假定能放进一个小数组；需确定有界表示后再冻结上限。
- **HTTPS**：当前Mbed TLS只编入安全包算法，没有TLS握手/X.509客户端。库默认TLS输入和输出内容缓冲各16384 B，仅内容就32768 B，还需记录开销、证书链、握手、会话、密码工作区、HTTP头/URL、下载块及执行栈。文件分块1 KiB不能推导TLS缓冲也只需1 KiB。TLS记录长度、证书/认证方式及服务器兼容性未冻结，不能给出已通过的总峰值；也不能以关闭证书验证或改明文作为内存优化。
- **并发**：下载阶段按现有需求仍允许采样、持久化、MQTT及结果上报，不假定它们全停。TLS与MQTT可能各占一个TCP连接；下载完成后应按真实生命周期核对TLS释放与安全包认证的重叠，当前仅能分别列预算，不能凭设想共享缓冲。TF升级和Boot恢复不需要同时保留TLS会话。
- **DMA与CCM**：网卡池、DMA实际访问的SDIO/UART缓冲留普通SRAM。仅CPU处理的点位、解析或TLS工作区可进一步评估CCM，但现有C堆不会自动使用CCM，必须检查分配器、所有权、初始化和传输复制路径。正式设计中“CCM暂保留”的文字与当前源码已有分配不一致，本预算按源码计数；本轮未新增迁移或修改云文档。

### 预算结论与下一阶段

源码预算审查已完成，**当前布局不通过整机资源准入**；配置完整容量、HTTPS握手峰值和全调用链栈峰值尚未关闭。需要先完成有证据的内存调整，再增加完整功能，不能通过未绑定模块、降低已验证网络池或忽略动态分配获得表面余量。

Modbus已完成固定4站容量调整。建议下一阶段依次处理应用AES ROM查表、M2/M3补传工作区；保持Boot分区及DMA边界。每项收益按新map核对，不能提前累计为已释放。随后给配置与HTTPS分配明确容量及保留余量；TLS超过剩余预算时，应调整内存组织或评审硬件/容量取舍，而非省略安全校验。

闭合条件：完整入口与实际网络参数下的map通过，三类堆及每条任务调用链均有独立预算；再在正常采样、双连接下载、重连、配置导入及安全包认证场景测量最小空闲堆、最大空闲块和栈高水位，验证DMA缓冲地址。具体安全余量需随最终结构及实测冻结，当前没有将任意百分比冒充验收标准。

## 看门狗交接约束

统一方案的执行配置已于2026-11-10接入：普通Boot及BootRecoveryTest在GPIO/USART1/SPI2就绪后启动IWDG，收包/认证/安装按固定期限和实际进展刷新；调试/测试启动诊断软件上限15000 ms，普通BootSizeCheck无DEBUG及测试根，但同样具备完整运行路径。最终交接要求已启狗且可信App检查通过，App早期接管后由Monitor监督。仅只读诊断不提前启狗。当前仍为256分频、4095重装值，统一硬件预算及实板复位/时序尚未验收，不能视为已满足拟定≤8 s目标。

## DMA 与中断

NVIC 使用 4 位抢占优先级、无子优先级。**NVIC 数字越小优先级越高**；调用 FreeRTOS 中断安全 API 的普通外设 IRQ，数值不得小于 5。DMA 的 High/Medium 等仲裁等级与 NVIC 优先级分别配置。

| 请求 | DMA 流 / 通道 | 模式 / DMA 优先级 | DMA IRQ / 外设 IRQ 抢占优先级 |
| --- | --- | --- | --- |
| USART3 RX | DMA1 Stream1 / Ch4 | Circular / High | 5 / USART3=5 |
| USART3 TX | DMA1 Stream3 / Ch4 | Normal / High | 5 / USART3=5 |
| USART2 RX | DMA1 Stream5 / Ch4 | Circular / Medium | 6 / USART2=6 |
| USART2 TX | DMA1 Stream6 / Ch4 | Normal / Medium | 6 / USART2=6 |
| SDIO RX/TX | DMA2 Stream3 / Ch4 | Peripheral Flow Control / Very High；Word、FIFO Full、INCR4 | 5 / SDIO=5 |
| USART1 TX | DMA2 Stream7 / Ch4 | Normal / Low | 7 / USART1=7 |

SDIO生成配置保留一个复用DMA流；当前Storage_Task文件路径使用限时同步轮询回调。SPI2 后续若增加 DMA，须重新检查与 USART3 TX 等流的冲突。ETH 使用独立 DMA，ETH IRQ=5；TIM7 IRQ=5；TIM6、SysTick 和 PendSV 为 15。

## 任务入口与初始预算

**CMSIS-RTOS2 任务优先级数字越大越高**，与上面的 NVIC 规则不同。以下为2026-11-11按键升级接入后的装配源码配置，不是实测峰值；接入后按完整调用链及栈高水位复核。

| 主责 / 用途 | 初始化 / 任务入口 | 任务优先级 | 静态栈 |
| --- | --- | --- | --- |
| M3 存储 | `Storage_Init` / `Storage_Task` | Normal，24 | 6KiB |
| M1 配置维护 | `Config_Init` / `Config_Task` | BelowNormal，16 | 512B |
| M1 Modbus | `Modbus_Init` / `vModbusPollTask` | AboveNormal，32 | 2KiB |
| M2 MQTT | `MqttClient_Init` / `MqttClient_Task` | Normal，24 | 6KiB |
| M2 遥测 | `Telemetry_Init` / `Telemetry_Task` | BelowNormal，16 | 2560B |
| M4 监督 | `Monitor_Init` / `Monitor_Task` | AboveNormal，32 | 2KiB |
| M4 TF升级 | `UpgradeTf_Init` / `UpgradeTf_Task` | Normal，24 | 6KiB |
| 默认启动任务 | `StartDefaultTask` → `App_Entry` | Normal，24 | 4KiB |

Storage、Modbus、监督和TF升级已绑定；Config、MQTT、Telemetry入口仍为`NULL`。七组模块栈的源码配置合计25KiB，实际保留量受链接回收影响，以map为准。存储、监督及升级栈使用普通SRAM，其余模块栈标记为CCM，不能将栈缓冲交给DMA。按键接入较此前已恢复版本增加8712 B普通SRAM，包含6144 B升级栈、TCB/状态和实际保留的接收工作区。默认启动任务装配完成后退出；监督任务在网络及业务初始化前启动。ETH接收/tcpip线程由网络适配创建，优先级约定为High（40）/AboveNormal（32），不在装配层重复创建。

初始化在调度器运行后准备本模块基础对象，耗时恢复放进所属任务。就绪状态通过 `app_readiness.h` 上报；初始化或任务创建成功不等于外设/业务就绪。存储队列、暂停/结算/同步和健康报告已接入；TF只授权本次按键操作，真实信任资料、网络权限及其他模块回调仍待齐备。
